# ADR-003: Ack messages only after the database commit

## Status
Accepted

## Context
The worker moves each transaction from the `transactions.received` queue into Postgres.
Between "message taken" and "row saved" things can go wrong: the worker can crash,
the database can be down, the app can be restarted. When the worker sends the ack
decides what a crash costs us: a lost transaction or a duplicate one.

## Options considered
1. **autoAck: true.** RabbitMQ deletes the message the moment it's delivered.
   If the worker crashes mid-save, the transaction is **lost**.
2. **Ack before saving.** Same problem: a crash between the ack and the save
   **loses** the transaction.
3. **Ack after the save commits.** A crash between the save and the ack means
   RabbitMQ redelivers the message, so it may be **processed twice**, but it's
   **never lost**.

## Decision
Option 3: manual ack, sent only after `SaveChangesAsync` succeeds.
For a bank, a lost transaction is unacceptable, while a duplicate can be detected.
This gives **at-least-once delivery**, combined with an **idempotent** consumer.

**How duplicates are handled:** the table's primary key is the message's
`TransactionId` (not generated by the database). A redelivered message hits a
unique-key violation (Postgres 23505), which the worker treats as
"already processed" and acks.

**How each failure is handled:**
| Failure | Example | Reaction |
|---|---|---|
| Broken message | invalid JSON, missing fields | nack, no requeue (dropped) |
| Duplicate | redelivery after a crash | ack |
| Temporary | Postgres down, timeout, shutdown | wait 2s, requeue |
| Unknown | unexpected bug | nack, no requeue, logged as error |

**Verified by tests:**
- Postgres stopped while a message was in flight: the message was retried and
  saved as soon as Postgres came back.
- Worker killed between the save and the ack (breakpoint, then stop): the message
  went back to the queue, was redelivered on restart, acked as a duplicate, and
  stayed one row.

## Consequences
**Good:**
- No transaction is lost when the worker crashes or the database is down.
- Broker duplicates are harmless.

**Bad / trade-offs:**
- At-least-once, not exactly-once: every step in the consumer must be safe to repeat.
- **Client duplicates are not caught yet.** If a client resends the same request,
  the API creates a new `TransactionId`. Fix: unique constraint on `ExternalId` (Week 3).
- Retries are crude: a fixed 2s delay with no limit. Fix: retries with growing
  delays and a retry limit (Week 3).
- Dropped messages are gone for good until there's a dead-letter queue (Week 3).
